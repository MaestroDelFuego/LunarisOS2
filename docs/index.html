MYOS Developer Guide

Getting Started

🟡 In Development

MYOS is being built incrementally with a strong emphasis on a stable x86-64 UEFI foundation before more ambitious desktop features are added.

The kernel now renders the canvas.png wallpaper and has a first reusable GUI layer. The current GUI demonstration is one pointer-driven test button, not a complete desktop.

Project Goals

  • Boot on standard x86-64 hardware and QEMU.
  • Provide a graphical desktop inspired by classic Windows XP.
  • Support persistent storage and built-in applications.
  • Keep the architecture modular and testable.

System Overview

The current architecture separates the boot flow from later kernel and GUI subsystems. This keeps the first milestone stable while allowing additional layers to be introduced in order. 

UEFI firmware
  ↓
Kernel entry point
  ↓
              GOP wallpaper renderer, desktop launcher, and window manager
  ↓
Future GUI, filesystems, and apps

Boot Process

The boot flow begins in UEFI, where the kernel is loaded and executed as an EFI application. The initial milestone prints diagnostics, prepares a framebuffer target, and halts safely if an unrecoverable error occurs.

Kernel

🟡 In Development

The kernel remains intentionally minimal at this stage. It locates the UEFI boot environment, outputs state information, and exposes the foundation needed for later memory management and scheduling work.

Memory

🟡 Planned

Memory detection and management will move from placeholder data to real UEFI memory map scanning once the initial boot environment is proven stable.

Filesystem

🟡 In Development

The no_std myos-filesystem crate implements format/mount and file list, read, write, overwrite, and delete operations over 512-byte blocks. Its initial format is a small MyOS-specific fixed-directory filesystem with contiguous file extents.

Host tests use an in-memory block device and verify data survives unmount/remount. The kernel does not yet have a block-device driver, so this filesystem is not yet attached to persistent QEMU or physical storage.

Source: filesystem/src/lib.rs

Graphics

🟡 Planned

The GOP framebuffer selects a supported display mode and renders the root canvas.png wallpaper with aspect-preserving cropping. A separate GOP painter draws clipped rectangles, bitmap text, and buttons. QEMU visual verification is still pending.

GUI Framework

🟡 In Development

The no_std myos-gui-core crate contains reusable geometry, button state, and a fixed-capacity window manager. The kernel paints overlapping windows and supports keyboard focus, movement, maximize/restore, close, and test-window creation.

QEMU verified Start-menu open, Window Demo launch, and Escape close using the keyboard. The taskbar includes a runtime clock and open-window buttons. Mouse delivery is unavailable with the tested firmware setup; native mouse drivers, resize handles, more menu entries, and applications remain unimplemented.

Sources: gui-core/src/lib.rs, kernel/src/gui.rs

Window Manager

🟡 In Development

The current window manager stores a fixed number of windows, tracks focus and z-order, and supports minimize, maximize, restore, close, and title-bar dragging. QEMU keyboard testing verified movement, focus cycling, button activation, maximize/restore, close, and reopen. Mouse delivery is not available with the tested firmware setup.

Desktop

🟡 In Development

The current desktop displays the canvas.png wallpaper and a working Window Demo shortcut. Enter or Space launches the window-manager demo. A desktop icon grid, context menu, taskbar, Start menu, system tray, and real applications remain future work.

Taskbar

🟡 In Development

The taskbar currently renders a Start control, buttons for open windows, and a clock read from UEFI runtime time. Window buttons and pointer activation are wired, but pointer delivery is not available in the tested QEMU firmware setup.

Start Menu

🟡 In Development

Press F2 to open the Start menu. Its only entry is Window Demo, which opens the working window-manager demo. Arrow keys select entries, Enter or Space activates the selection, and Escape closes the menu. No nonfunctional application or shutdown entries are shown.

Notepad

🔴 Planned

Notepad will become the first major user-facing application. It will provide text editing, file open/save flow, and persistent document support through the filesystem layer.

Explorer

🔴 Planned

The Explorer-like file manager will eventually provide navigation, folder and file operations, and opening files in the appropriate application.

Calculator

🔴 Planned

The calculator will support standard arithmetic operations and later increased capability as the GUI framework matures.

Terminal

🔴 Planned

The terminal will provide a small CLI surface for filesystem and system commands to support development and administration.

Settings

🔴 Planned

Settings will expose only the options that are genuinely implemented, starting with display-related basics and system information.

Building

Build the workspace from the project root using the Rust toolchain and the x86_64-unknown-uefi target. 

cargo build --workspace --target x86_64-unknown-uefi

QEMU

QEMU is the preferred environment for testing the kernel before any physical hardware attempt. OVMF is the standard virtual EFI firmware used for this path.

Debugging

Logging and diagnostics remain essential throughout the project. The early milestone prints to the UEFI console and keeps a serial-oriented abstraction in place for later hardware debugging.

Testing

The initial milestone focuses on compileability and boot-path sanity. The next milestone will add graphics and input validation in QEMU.
